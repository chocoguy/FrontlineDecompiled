**Session 3 (2026-10-11): boot crash.** The first batch 4 test crashed at boot ("Invalid read from 0x4c"
in `CScreenFieldMode::SetCurrent`: `g_screen` had a null vtable). Bisecting by unit group gave
contradictory results. Instrumented builds showed the cause: `g_screen` was never constructed
because `__init_cpp` skipped the first five `.ctors` entries.

- The retail loader (`sys/main.dol`) `memset`s each ELF segment and then `DVDRead`s it straight to
  its address. DVD DMA ignores the low 5 bits of the destination, so a segment that is not
  32-byte aligned loads shifted down.
- dtk's linker script aligned `.ctors` to 4 bytes. Batch 4's size change put it 0x14 past a
  boundary, so the table loaded 0x14 bytes low and the first five constructors were skipped,
  including `__sinit_Moh2_cpp`.
- Fix: `config/GMFE69/splits.txt` now uses `align:32` for every section, as in the retail ELF.
  A simulation of the loader on the fixed build shows all 53 constructors run and memory matches
  the ELF exactly. `regress.py` unchanged.
- No batch 4 source change was needed.
